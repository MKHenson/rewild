# Rust and WASM

Some worker code is written in Rust and compiled to WebAssembly. This page shows how to set up the toolchain, build and test the module, and add Rust code to it.

## Set up the toolchain

You need Rust, the `wasm32-unknown-unknown` target, and `wasm-pack`.

### macOS

```sh
brew install rustup wasm-pack
rustup-init
rustup target add wasm32-unknown-unknown
```

Homebrew does not put the Rust commands on your `PATH`. Add this line to `~/.zshrc`, then open a new terminal:

```sh
export PATH="/opt/homebrew/opt/rustup/bin:$PATH"
```

### Windows

1. Install Visual Studio Build Tools with the "Desktop development with C++" workload. Rust needs its linker for the host build steps.
2. Run `rustup-init.exe` from https://rustup.rs and accept the default `x86_64-pc-windows-msvc` toolchain.
3. In a new terminal:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
```

### Check the setup

```sh
rustc --version
cargo --version
wasm-pack --version
```

## Build and test

Run these from the repo root.

| Command | What it does |
| --- | --- |
| `npm run build:wasm` | Builds the module into `packages/rewild-wasm/pkg/`. |
| `npm run test:wasm` | Runs the Rust tests (`cargo test`). |
| `npm test` | Builds the module, runs the Rust tests, then the JS tests. |
| `npm run bench` | Builds the module, then benchmarks the worker code. JS and WASM cases run side by side. |

`npm run build`, `npm start` and `npm run watch` build the module first. A build with no changes takes under a second.

The watch mode does not watch the Rust code. After you change Rust code, run `npm run build:wasm`.

## Add Rust code

1. Write the logic in a library crate under `packages/rewild-wasm/crates/`. Keep it plain Rust with no JS types, so `cargo test` can test it. To add a crate, create its folder with a `Cargo.toml`. The workspace finds it.
2. Expose it in `crates/rewild-wasm/src/lib.rs` with `#[wasm_bindgen]`. Make one call do a whole job, such as one BVH build. Each call copies its input into WASM memory and its output back out.
3. Call it from TypeScript through a small wrapper, like `lib/acceleration/BVHWasm.ts`. Load the module once per worker with `loadRewildWasm` (`lib/wasm/RewildWasm.ts`). Tests and benchmarks use `loadRewildWasmSync`.
4. Test the Rust logic with `cargo test`. Add a Jest spec that checks the WASM output against the JS version, like `BVHWasm.spec.ts`. Use `@jest-environment node`, because jsdom has no `TextDecoder`.
5. Add a WASM case to `packages/rewild-renderer/bench/main.ts` next to the JS case.

The tests do not require WASM output to match JS output bit for bit. They check the properties that matter, so the Rust code is free to use SIMD or a different algorithm.

## Write fast Rust for WASM

- **Avoid `f32::min`, `f32::max` and `clamp` in hot loops.** WASM min and max must propagate NaN and order -0 below +0. ARM does that in one instruction. On x64, V8 emits several instructions for each call. Use a compare and select, like `fast_min` in the `bvh` crate, on values that cannot be NaN. In the BVH builder this made x64 builds about 2.9x faster.
- **Benchmark on x64 and ARM.** A cost that one CPU hides can be large on the other.

## Reference

### Layout

| Path | Contents |
| --- | --- |
| `packages/rewild-wasm/Cargo.toml` | The Cargo workspace and the release profile. |
| `packages/rewild-wasm/.cargo/config.toml` | Turns on 128-bit SIMD for the WASM target. |
| `packages/rewild-wasm/crates/bvh/` | The BVH builder. A port of `BVHBuilder.ts`. |
| `packages/rewild-wasm/crates/rewild-wasm/` | The output crate. It exposes the library crates to JS. |
| `packages/rewild-wasm/pkg/` | Generated by `npm run build:wasm`. Not in git. |
| `scripts/build-wasm.mjs` | Runs `wasm-pack` on macOS and Windows. |

### One module

All library crates compile into one `.wasm` file. Each worker that uses it loads its own instance. esbuild emits the file with a content hash in its name, so the deploy can cache it for a year.

### BVH worker builds

The BVH worker builds with Rust by default. Set `BVHConfig.wasmWorkerBuilds` to `false` to build in JS. If the module fails to load, the worker logs a warning and builds in JS. Synchronous builds, under `asyncBuildThreshold` triangles, always use JS.
